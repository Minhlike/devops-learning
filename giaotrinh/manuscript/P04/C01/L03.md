“Đã test bản v1.4” là một câu chưa đủ chặt. v1.4 có thể là tên tag, tên nhánh, chuỗi trên giao diện phát hành hoặc nhãn image. Khi cần truy vết, tôi hỏi thêm: tên ấy đã được giải ra commit nào trong kho nào, vào thời điểm nào, và artifact nào đã được tạo? Git cung cấp các định danh và tham chiếu cần thiết để trả lời nửa đầu câu hỏi; nửa sau thuộc hệ thống build.

Commit identity là ID của object commit, hình thành từ root tree, parent và metadata của chính commit. **Ref** là tên lưu một object ID. Branch là ref dự kiến dịch theo commit mới; tag thường dùng để đánh dấu một điểm. `HEAD` thường là tham chiếu tượng trưng tới branch đang checkout. Ví dụ `HEAD → refs/heads/main → D`: commit mới `E` sẽ làm `main` trỏ `E`, còn object `D` và parent chain không bị sửa. Sơ đồ dưới đây tách rõ mũi tên tên–object và quan hệ parent giữa các commit.

Khi checkout một commit theo ID thay vì branch, `HEAD` ở trạng thái **detached**: nó trỏ trực tiếp tới commit ấy. Bạn vẫn có thể tạo commit mới; commit mới nối với commit đang checkout, nhưng không tự đẩy một branch cũ đi theo. Nếu chuyển sang branch khác mà không lưu một ref cho commit mới, sau này chỉ có thể tìm lại nếu object và dấu vết tham chiếu còn tồn tại. Trước khi rời nhánh thử, tạo branch hoặc ghi ID cần giữ. `git symbolic-ref --short HEAD` giúp phân biệt HEAD tượng trưng; lệnh này báo lỗi trong detached HEAD, còn `git rev-parse HEAD` vẫn trả ID commit hiện tại.

Trong cách gọi của Git, một tag nhẹ thường trỏ tới object được đánh dấu, trong khi annotated tag là một object riêng có tên, thông điệp, người tạo và đích; nó cũng có thể mang chữ ký nếu được ký và xác minh đúng cách. Cả hai là nhãn, không phải chứng thư rằng code đã qua kiểm thử. Theo thông lệ phát hành, không tự dời tag đã công bố vì người khác có thể đã ghi lại đích cũ. Một commit được ghi bằng ID đầy đủ là định danh đối tượng trong object format của kho, còn tên branch/tag cần resolve tại thời điểm dùng. Chữ ký và chính sách bảo vệ ref là những kiểm soát khác, không xuất hiện chỉ nhờ có tag.

Remote là một repository khác được cấu hình bằng tên như `origin`. `origin/main` là remote-tracking ref trong kho cục bộ: bản ghi về ref phía remote sau lần fetch tương ứng. `git fetch origin` trao đổi object và cập nhật các remote-tracking ref theo refspec; nó không tự nhập thay đổi ấy vào branch `main` cục bộ. Nếu server đã đi tiếp mà bạn chưa fetch, `origin/main` có thể cũ. Nếu bạn vừa fetch, nó chỉ phản ánh điều server quảng bá vào thời điểm trao đổi, không đóng băng server mãi về sau. Hãy ghi commit ID từ cả hai phía khi phải quyết định merge hay release, thay vì bảo “origin/main chắc là bản mới nhất”.

Xét đồ thị giả định `A → B → C → D`. `main` trỏ `D`, tag `v1.4` và branch `release/1.4` cùng trỏ `B`, còn `origin/main` chưa cập nhật vẫn trỏ `C`. `git rev-parse main`, `git rev-parse v1.4^{}` và `git rev-parse origin/main` giúp so đích đã resolve; toán tử `^{}` bóc tag có chú giải để lấy object được đánh dấu. Kết quả `D/B/C` không chứng minh server hiện ở `C`. `git log --graph --decorate --all` cho thấy những ref cục bộ nào dẫn tới commit nào. Quan hệ parent cho phép hỏi `B` có là tổ tiên của `D` không; `git merge-base --is-ancestor B D` trả status phù hợp nếu thay `B`/`D` bằng ID hoặc ref thật. Đừng suy tổ tiên chỉ từ thời gian hay SHA nào “lớn” hơn.

Một object được gọi là **reachable** nếu có đường từ một ref (hoặc gốc giữ object khác) đi theo tham chiếu tới nó. Dời `main` từ `D` sang một commit mới có parent `D` không xóa `D`, vì đường cha vẫn dẫn tới nó. Ngược lại, giả sử commit thử `E` chỉ có nhánh riêng trỏ tới nó: sau khi xóa nhánh, E có thể trở thành unreachable từ các ref hiện tại. Reflog ghi những lần ref và HEAD từng đổi trong kho cục bộ, nên đôi khi giúp tìm tip cũ; thời hạn lưu, chính sách dọn rác và bản sao khác nhau khiến nó không phải backup. Tôi ghi ID và backup theo chính sách trước các thao tác viết lại, thay vì coi `git reflog` là lời hứa phục hồi.

Đến đây, ta có ba lớp khác nhau: byte được lưu thành object, tên ref dẫn tới commit, và artifact có digest riêng sau build. Một commit có thể được build với dependency hoặc cấu hình khác nhau; commit ID không tự định danh duy nhất binary hay image. Khi phần học về phát hành nói đến phát hành, chuỗi chứng cứ cần nối commit đã resolve, đầu vào build, digest artifact, kiểm thử và phiên bản đang chạy. Trước mắt, mối quan hệ parent sẽ giúp ta xác định khi nào chỉ cần dời ref và khi nào phải hợp nhất hai nhánh công việc.
