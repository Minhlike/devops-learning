Một file trong thư mục dự án có thể đổi tên mà vẫn giữ nguyên từng byte. Nghe rất hiển nhiên; với Git, câu hỏi thú vị hơn là: đối tượng nào trong lịch sử đổi theo tên ấy? Tôi bắt đầu từ câu hỏi này vì người mới thường nghĩ commit là bản sao nguyên thư mục, còn người dùng lâu năm đôi khi lại nói Git “lưu các diff”. Cả hai hình dung đều bỏ lỡ cấu trúc cần thiết để giải thích rename, branch và merge.

Trong phần này, `atlas` là repository **giả định**. Các chữ `A`, `B`, `C` là nhãn để đọc đồ thị, không phải SHA thật hay output đã chạy. Git gọi mỗi bản ghi nội dung có định danh là một **object**. Ba loại cần nắm trước là blob, tree và commit. Object có thể được Git nén, đóng gói hoặc biểu diễn hiệu quả trên đĩa; mô hình bên dưới nói về quan hệ logic, không hứa mỗi snapshot là một bản sao vật lý đầy đủ.

Một blob chứa nội dung tệp, không chứa tên tệp. Nếu `app.conf` có đúng các byte `port=8080` và một bản khác ở đường dẫn `archive/app.conf` có cùng byte, cả hai có thể cùng tham chiếu một blob. Blob không biết nó nằm ở thư mục nào, ai sửa hay khi nào sửa. Đây là một phân tách đáng giá: nội dung có thể được nhận diện và tái sử dụng độc lập với cách đặt tên.

Tên xuất hiện trong **tree**. Mỗi entry của tree gắn tên với mode và object ID của blob hoặc tree con. Chẳng hạn tree gốc của `atlas` có entry `app.conf → B1` và `notes.txt → Bn`; một thư mục con sẽ là entry trỏ tới tree khác. Mode thường cho biết file thường không thực thi `100644`, file thực thi `100755`, symlink `120000` hoặc tree thư mục `040000`. Git không ghi toàn bộ ACL hay mọi metadata của hệ thống tệp vào mode này. Vì vậy đổi mode thực thi có thể đổi tree dù byte trong blob giữ nguyên. Sơ đồ dưới đây cho thấy đường đi từ commit tới tên tệp và nội dung; chiều mũi tên là tham chiếu object, không phải luồng chạy chương trình.

Một **commit** trỏ tới root tree, ghi metadata như tác giả, người tạo commit, thời điểm và thông điệp, cùng không hoặc nhiều commit cha. Commit đầu có thể không có cha; commit thường có một cha; merge commit có thể có hai cha. Đọc commit từ root tree để biết snapshot file ở thời điểm ấy, rồi đi theo parent để biết snapshot này nối với lịch sử nào. Cấu trúc cha tạo thành đồ thị có hướng không chu trình. Hai commit có thể trỏ tới cùng một root tree nhưng mang parent hoặc metadata khác, nên ID commit vẫn khác. Git lưu snapshot được liên kết bằng quan hệ cha–con; `git diff` mới là phép so hai snapshot để trình bày thay đổi.

Định danh object không phải số thứ tự do server cấp. Git băm byte của header gồm loại object, một dấu cách, độ dài nội dung, byte NUL và chính nội dung; object format của repository quyết định thuật toán. Nhiều kho dùng SHA-1; Git cũng hỗ trợ kho SHA-256. Một prefix SHA mà `git log --oneline` in ra chỉ là cách viết rút gọn đủ phân biệt trong ngữ cảnh hiện tại. Định danh giúp đối chiếu nội dung được tham chiếu, nhưng tên tác giả trong commit có thể do người tạo tự khai: hash không chứng minh danh tính người viết, mã đã được review hay artifact xây từ mã ấy có an toàn.

Ta thử suy luận trên ba commit nhỏ, giả sử nội dung chỉ có một dòng và mode giữ nguyên. Ở `C1`, `app.conf` chứa `port=8080`: blob `B1`, root tree `T1`. Ở `C2`, chỉ đổi tên thành `service.conf`: blob nội dung vẫn là `B1`, nhưng tree gốc thành `T2` vì tên entry khác; commit cũng mới vì tree và parent mới. Ở `C3`, sửa byte `8080` thành `9090`: blob thành `B2`, tree thành `T3`, commit lại đổi. Nếu file nằm trong cây thư mục sâu, tree của thư mục chứa file và những tree tổ tiên cũng đổi; tree ở nhánh thư mục không liên quan có thể giữ nguyên. Sơ đồ phía trên cố tình vẽ cả tham chiếu dùng lại để bạn thấy “mới” không đồng nghĩa mọi object bên dưới đều mới.

Một phép kiểm có thể làm trong repository thử: sau mỗi commit, đọc `git cat-file -p HEAD` để xem trường `tree` và `parent`, rồi `git ls-tree -r HEAD` để xem tên, mode và ID blob. `git hash-object service.conf` tính ID cho nội dung file hiện có nhưng không tự chèn object vào kho nếu không dùng tùy chọn ghi; đừng suy rằng file hiện trên đĩa đã nằm trong commit. Dùng ID đầy đủ khi cần ghi bằng chứng qua nhiều kho. Nếu kết quả khác dự đoán, trước tiên kiểm byte xuống dòng và mode: một ký tự xuống dòng hoặc bit thực thi khác cũng là thay đổi thật.

Git có thể trình bày cặp xóa–thêm giữa `C1` và `C2` như một lần rename. Đó là phép suy luận của diff khi so hai tree theo độ giống nội dung, có ngưỡng và tùy chọn; bản thân blob và tree không chứa một sự kiện “đổi tên” được lưu riêng. Người điều tra lịch sử vì thế nên phân biệt dữ kiện object với cách lệnh diff diễn giải chúng. Sự phân biệt ấy sẽ còn quan trọng khi ta thấy Git xử lý conflict: máy có thể tìm ra những byte khác nhau, nhưng quyết định ý nghĩa của thay đổi vẫn thuộc về người đọc.
