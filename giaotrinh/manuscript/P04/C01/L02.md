Working tree là những tệp đang thấy và sửa bằng trình biên tập. Index là snapshot dự kiến cho commit kế tiếp; `git add` chép nội dung hiện tại của đường dẫn vào index tại thời điểm chạy. `HEAD` thường là tham chiếu tượng trưng tới branch đang checkout, còn branch ref trỏ tới một commit. Khi tạo commit, Git ghi tree từ index, đặt commit mới có cha là commit tại `HEAD`, rồi dịch ref của branch hiện tại sang commit mới. Sửa tệp sau `git add` không tự cập nhật index; commit có thể chứa bản cũ trong khi working tree vẫn có sửa đổi mới.

Giả sử `timeout_ms` trong commit hiện tại là `1000`. Ta sửa working tree thành `2000`, stage, rồi sửa tiếp thành `3000`. Lúc ấy `HEAD` giữ `1000`, index giữ `2000`, working tree giữ `3000`. `git diff --cached` so `HEAD` với index, còn `git diff` mặc định so index với working tree. Nếu commit ngay, snapshot mới ghi `2000`; muốn ghi `3000` phải stage lại và kiểm tra diff. Đây là lý do `git status` và diff trước commit có giá trị hơn lời khẳng định “tôi đã lưu file”. Tệp chưa được theo dõi chưa tự có trong index.

Index còn lưu metadata đường dẫn và mode, không chỉ một “danh sách file đã chọn”. Một thao tác `git add -p` có thể stage một hunk sửa lỗi nhưng để hunk debug lại trong working tree. Khi đó `git diff --cached` là nội dung thực sự được đưa vào commit; `git diff` là phần chưa stage, và cả hai đều có thể cùng nhắc tới một tệp. Nếu test chạy trên working tree đang chứa hunk debug, test xanh chưa chứng minh snapshot sẽ commit chạy xanh. Muốn kiểm tra chính xác nội dung đã stage, xem diff staged rồi thử nó trong một checkout tạm hoặc dùng CI trên commit tạo ra từ index; không xóa working tree hiện tại để lấy bằng chứng.

Lần theo thêm một chuỗi có thể tự làm trên repository thử: tạo file `setting.txt` chứa `1000`, commit; sửa thành `2000`, `git add setting.txt`; sửa tiếp thành `3000`; quan sát `git show HEAD:setting.txt`, `git show :setting.txt` và nội dung file trên đĩa. Dự đoán lần lượt là `1000`, `2000`, `3000`. Sau commit, branch mới trỏ tới tree chứa `2000`; `3000` vẫn là thay đổi chưa stage. Có thể sửa lại bằng `git add` rồi commit kế tiếp, hoặc xem xét sửa commit nếu chưa chia sẻ lịch sử. Tránh dùng `reset --hard` để “dọn” trước khi đối chiếu vì nó làm mất bằng chứng trong working tree.

Sự phân tách này giải thích một lỗi review thực tế: tác giả nói đã sửa secret trong bản cấu hình, nhưng index vẫn chứa bản cũ. Kiểm tra file trên đĩa là chưa đủ; phải kiểm staged diff và sau commit kiểm tree của chính commit được đẩy. Nếu secret đã đi vào commit hoặc remote, chỉ xóa khỏi commit mới không thu hồi secret: cần quy trình thu hồi/đổi khóa và xử lý lịch sử theo phạm vi phân phối. Cơ chế index giúp ta biết byte nào sắp được ghi vào lịch sử, trước khi bàn tới merge hay rebase ở các bài sau.
