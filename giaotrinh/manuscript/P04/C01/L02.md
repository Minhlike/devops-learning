Ở bài trước, commit là một snapshot đã ghi. Nhưng bạn đang gõ trong trình biên tập thì snapshot ấy chưa thay đổi. Giữa hai trạng thái còn một lớp dễ bị bỏ qua: index. Nếu phải chọn một mô hình để dự đoán lệnh Git, tôi chọn ba ảnh của cùng một đường dẫn tại cùng một thời điểm: `HEAD`, index và working tree. Chúng có thể khác nhau mà repository vẫn hoàn toàn bình thường.

**Working tree** là các tệp hiện trên đĩa để bạn sửa và chạy. **Index**, còn gọi là staging area, là tập entry đường dẫn, mode và object ID dự kiến trở thành tree của commit kế tiếp; ở bài merge, nó còn có các stage chưa giải conflict. `HEAD` thường là tham chiếu tượng trưng tới branch hiện tại, còn branch ref trỏ tới commit đang checkout. Đây là ba vai trò khác nhau: một ảnh đã ghi, một ảnh chuẩn bị ghi, và một ảnh đang làm việc. Sơ đồ dưới đây vẽ cùng một giá trị ở ba thời điểm để chống lại cảm giác “sửa file tức là sửa commit”.

Bắt đầu với `atlas` ở commit `B`: `app.conf` có `timeout_ms=1000`. Bạn sửa working tree thành `2000`; lúc này `HEAD=1000`, index vẫn `1000`, working tree là `2000`. Khi chạy `git add app.conf`, `git add` chép nội dung hiện tại của đường dẫn vào index: index thành `2000`. Rồi bạn sửa tiếp thành `3000` mà không add lại. Kết quả là `HEAD=1000`, index `2000`, working tree `3000`. Nếu commit ngay, Git viết tree từ index và tạo commit chứa `2000`; lần sửa `3000` vẫn nằm trên đĩa, chưa stage. Việc trình biên tập báo “đã lưu” chỉ nói về working tree.

Ta có thể quan sát mà không đoán. `git status --short` phân loại đường dẫn theo thay đổi giữa `HEAD`–index và index–working tree; một tệp có thể có dấu ở cả hai cột. `git diff --cached` (hay `--staged`) so `HEAD` với index, nên cho thấy `1000 → 2000`. `git diff` mặc định so index với working tree, nên cho thấy `2000 → 3000`. `git show HEAD:app.conf` đọc bản trong commit; `git show :app.conf` đọc entry stage thường ở index. Với file thử mang tên `setting.txt`, cùng cú pháp là `git show :setting.txt`. Cuối cùng hãy mở file trên đĩa. Bốn phép đọc ấy trả lời bốn câu hỏi khác nhau; dùng đúng câu hỏi giúp tiết kiệm nhiều giờ tranh luận “máy tôi vẫn chạy”.

Index không chỉ biết “đã chọn file nào”. Với `git add -p`, bạn có thể stage hunk sửa timeout nhưng giữ một hunk bật debug ở working tree. Commit sắp tạo có thể là tổ hợp các hunk chưa từng đồng thời tồn tại như một file trên đĩa. Vì vậy test chạy trên working tree xanh chưa chứng minh snapshot trong index xanh. Hãy xem staged diff và kiểm snapshot sau commit trong checkout tạm hoặc CI trên đúng commit ID; trước đó có thể dùng `git diff --check --cached` để bắt lỗi whitespace, nhưng phép này không thay kiểm thử hành vi.

Một file mới chưa được theo dõi là **untracked**: nó hiện trong thư mục nhưng chưa ở index và chưa thuộc commit. File đã theo dõi có thể đồng thời **staged** và **unstaged** nếu add xong rồi sửa tiếp. File bị ignore thường không xuất hiện trong status mặc định, song quy tắc ignore không xóa object đã từng được ghi. Tôi thường đọc `git status` rồi hai diff trước khi commit; đó là cách kiểm quyết định “byte nào sẽ đi vào lịch sử”, không phải nghi thức để làm đẹp terminal.

Câu chuyện nguy hiểm hơn là secret. Giả sử bạn vô ý đưa `token=demo-secret` vào `app.conf` rồi `git add`. Sau đó bạn xóa dòng ấy trên đĩa, nhưng chưa add lại. Mắt nhìn working tree thấy sạch; index vẫn giữ blob có secret. `git diff --cached` mới tiết lộ thứ sắp được commit. Nếu secret chưa ra khỏi máy, sửa bản staged bằng add lại hoặc bỏ stage có chủ đích; `git restore --staged app.conf` đưa index của path về `HEAD` mà không phải xóa working tree. `git restore app.conf` theo mặc định lại chép từ index vào working tree và có thể làm mất sửa đổi chưa lưu của bạn. Cần đọc status/diff trước khi dùng lệnh phục hồi có tác động lên đĩa.

Nếu secret đã đi vào commit được đẩy hoặc log/artifact, một commit xóa dòng secret không làm bí mật cũ biến mất khỏi các bản sao. Khi ấy phải thu hồi hoặc xoay khóa theo phạm vi đã lộ, rồi mới quyết định xử lý lịch sử và hệ thống liên quan. Đây là lý do tôi dạy index trước merge: hiểu một lần chụp nội dung ở thời điểm `git add` giúp bạn xác định đúng biên giới giữa ý định, dữ kiện đã stage và lịch sử thật. Ở bài sau, ta đặt tên cho các commit ấy bằng branch, tag và remote-tracking ref.
