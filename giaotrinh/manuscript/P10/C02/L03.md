`--syntax-check` kiểm tra cấu trúc playbook, chưa kết nối và chưa xác nhận đường file, quyền hoặc hành vi module trên host thật. `--check` dự đoán thay đổi mà không ghi trên managed node với module hỗ trợ; module không hỗ trợ có thể bị bỏ qua, task dùng kết quả task trước có thể không được đánh giá như lúc apply. `--diff` hiển thị chênh lệch khi module hỗ trợ và có thể làm lộ dữ liệu nhạy cảm trong template, nên không bật tùy tiện cho secret. Check mode không dự báo được API sẽ từ chối, ổ đĩa hết chỗ, handler restart thất bại hay request sau restart sai. Chạy trên một host đại diện và kiểm tra sau thay đổi vẫn cần thiết.

Nếu host lỗi trước lúc handler được chạy, handler thường không chạy trên host đó; `force_handlers` thay hành vi này nhưng có thể khiến restart trên cấu hình chưa được xác minh.

Xét một play giả định có ba task: render template, đổi mode thư mục, rồi validate cấu hình; handler restart được notify chỉ khi template changed. Trong `--check`, task validate có thể không nhìn thấy file mới vì bước render chưa ghi thật; vì vậy “check xanh” không chứng minh handler sẽ restart an toàn khi apply. Trên một host thử có dữ liệu riêng, ghi checksum template, mode và trạng thái service trước/sau lượt đầu; lượt thứ hai phải `ok` ở các task hội tụ, không notify restart ngoài ý muốn. Nếu validation fail trước handler, cần xem lại file đang hiện hữu và trạng thái tiến trình, không áp `force_handlers` như một thuốc sửa tổng quát.

Một cách đọc recap có giá trị hơn chỉ nhìn `failed=0` là so với dự đoán trước chạy. Nếu chỉ mode thư mục drift, task file phải `changed`, task template phải `ok` và không có notify restart. Nếu template đổi nội dung, handler sẽ được xếp hàng; trước khi cho nó tác động dịch vụ, kiểm cú pháp file đích và điều kiện quyền/truy cập dữ liệu. `--check` không ghi file, nên một task validate đọc file hiện hữu có thể đang kiểm bản cũ chứ không phải bản sắp áp; đó là sự khác nhau giữa dự đoán thay đổi và kiểm thực trạng sau apply. Đặt tên từng bước kiểm trong log để biết cổng nào đã chạy thật.

Trên host thật, đưa thay đổi qua một máy thử hoặc một nhóm nhỏ, ghi phiên bản playbook, inventory, biến hiệu lực và checksum cấu hình trước khi sửa. Sau lượt đầu, kiểm mode bằng `stat`, cú pháp cấu hình bằng công cụ của dịch vụ, trạng thái process và một request nghiệp vụ. Sau lượt hai với cùng input, so checksum, recap và marker reload: nếu còn `changed` không dự kiến, truy task nào không hội tụ thay vì chấp nhận restart lặp. Với cấu hình có secret, không đưa `--diff` hoặc output module lên hệ log mở; dùng hash hoặc phép kiểm chức năng phù hợp mà không in giá trị.

Nếu task validate thất bại sau khi template đã thay, trạng thái cần báo là **partial change**: file trên host có thể đã mới nhưng handler chưa chạy, service có thể còn dùng cấu hình cũ trong bộ nhớ. Phương án sửa tùy hợp đồng dịch vụ: khôi phục file cũ đã lưu, sửa file mới rồi validate lại, hoặc cô lập host khỏi traffic trước khi reload. Không tự suy rollback đã xảy ra vì playbook trả lỗi. Hậu điều kiện phải nói rõ file trên đĩa, process đang dùng bản nào và request của người dùng ra sao.
