Trước khi xây pipeline, tôi muốn biết một đơn hàng là gì trong ví dụ này. Client gửi item và quantity; API trả ID; GET theo ID phải đọc lại đúng item, quantity và dấu vết request đã tạo. Nếu client không nhận response rồi gửi lại cùng ý định, hệ thống không được tạo đơn thứ hai. Đây là hợp đồng nghiệp vụ của fixture giáo dục, chưa có thanh toán, tenant, xác thực hoặc nghĩa vụ pháp lý của cửa hàng thật. Không viết test cho một điều chưa được định nghĩa: “đơn thành công” ở đây là transaction SQLite đã commit và record có thể đọc lại, không phải hàng đã giao.

Trong examples/orders_toolchain, app.py là HTTP process; test_app.py khởi động process với database tạm và kiểm qua HTTP; smoke.py chạy sau deploy qua cổng loopback; Dockerfile đóng gói app; local_pipeline.py nối test, image, registry, deploy và restore; deploy.compose.yaml chỉ nhận image theo digest. Một file ci.yml mô tả workflow cho repository sandbox. Bạn nên đọc cây ấy như các ranh giới trách nhiệm: test nguồn, thử artifact, publish artifact, chạy artifact, kiểm dữ liệu. Nếu dùng Compose file phát triển có trường build, bạn đang thử đường khác; đường phát hành dùng file deploy riêng không build.

SQLite là lựa chọn đủ nhỏ để nhìn transaction và volume, không phải database nhiều host. Bảng orders có ID, item, quantity, thời điểm, idempotency key, hash payload, request ID tạo, revision và instance tạo. ID trả ra được lưu trong cùng record. Khi đổi từ schema cũ, initialize_db thêm các cột còn thiếu và unique index, giữ row cũ; các row cũ không có request ID gốc, vì bằng chứng lịch sử không thể tự sinh sau sự kiện. Bản migration dạy một nguyên tắc: mở rộng schema tương thích trước khi yêu cầu code cũ/mới cùng đọc, không coi migration là một lệnh có thể đảo an toàn.

POST yêu cầu Idempotency-Key từ 1 đến 64 ký tự an toàn. Key có phạm vi toàn database của fixture; không có tenant nên không thể áp nguyên trạng cho hệ nhiều khách hàng. API chuẩn hóa hai trường nghiệp vụ rồi băm payload. Trong transaction BEGIN IMMEDIATE, nó tìm key đã có: cùng payload trả 200 với order ID cũ và replayed=true; payload khác trả 409; chưa có thì insert và sau commit trả 201. Unique index là tuyến phòng vệ ở database. Hai request đồng thời cùng key không được tạo hai record vì SQLite chỉ cho một writer giữ transaction ghi ở thời điểm đó; test khởi hai request thật để kiểm. Nếu database bận quá thời hạn, API trả 503; client có thể thử lại cùng key, nhưng phải tính deadline và giới hạn retry ở phía caller.

```python
with database() as conn:
    conn.execute("BEGIN IMMEDIATE")
    previous = conn.execute(
        "SELECT id,payload_hash FROM orders WHERE idempotency_key=?", (key,)
    ).fetchone()
    if previous and previous[1] != payload_hash:
        return self.respond(409, {"error": "idempotency_conflict"}, rid)
    # Nhánh replay hoặc INSERT tiếp tục trong cùng transaction.
```

Đoạn rút gọn trên giải thích khóa quyết định, không thay toàn bộ implementation. Trong code thật, nhánh replay trả ID cũ; nhánh insert ghi cả request ID, revision và instance. HTTP response chỉ được coi là thành công sau khi context manager commit. Tuy nhiên, một process crash giữa commit và gửi response vẫn để client ở trạng thái không chắc chắn; chính việc retry cùng key giúp client hỏi lại kết quả. Nó không giải quyết tác dụng phụ ngoài database như email gửi trước commit. Nếu sau này thêm email, phải thiết kế outbox hoặc cơ chế đối soát, không nhét lệnh gửi vào giữa transaction rồi hy vọng retry vô hại.

Input được kiểm giới hạn body và kiểu quantity: trong Python, bool là con của int, nên dùng type(value) is int để tránh nhận true như số lượng 1. API không log body; điều này giảm nguy cơ lộ dữ liệu nhưng làm điều tra payload khó hơn. Request ID từ client bị giới hạn ký tự/độ dài, hoặc server tạo ID mới. Nó là correlation ID, không phải credential. Idempotency key không được ghi thô vào log; hệ thực cần cân nhắc thời hạn lưu key, quyền truy xuất, chống đoán và chính sách xóa dữ liệu. Fixture giữ key theo vòng đời record để phép thử đơn giản; đó là một đánh đổi được ghi rõ.

Health và readiness khác nghiệp vụ. GET /healthz trả 200 nếu process trả lời. GET /readyz thử truy vấn SQLite; cờ FAIL_READINESS cho phép mô phỏng 503. Cờ FAIL_BUSINESS tạo trường hợp khó hơn: health/readiness cùng 200 nhưng POST trả 503. Test và pipeline phải phân biệt. GET /metrics đưa ra hai counter trong bộ nhớ; chúng reset khi process thay, không phải thống kê toàn dịch vụ. Log JSON có request ID, status, order ID và instance; GET record có origin_request_id/revision/instance. Từ đó ta nối request thử tới dữ liệu mà không khẳng định mọi request đều được quan sát.

Một phép kiểm tốt dùng database tạm, không sửa volume học tập hay dữ liệu thật. Các ca dương tạo rồi đọc đúng đơn, retry giữ ID, và hai POST cạnh tranh chỉ một record. Ca âm gồm số lượng âm, thiếu key, cùng key payload khác, readiness fail và lỗi nghiệp vụ khi readiness vẫn xanh. Không test nào chứng minh sức chịu tải hay an toàn production. Nó làm rõ hợp đồng mà artifact phải giữ ở các bước tiếp theo; nếu app sai ngay tại đây, registry và Kubernetes chỉ phát tán sai lầm nhanh hơn.

Đường lỗi quan trọng nhất nằm ở khoảng giữa quyết định của server và tri thức của client. Giả định transaction đã commit record o7, rồi kết nối TCP đứt trước khi response 201 tới browser. Browser chỉ biết “không nhận được câu trả lời”, không biết server đã ghi hay chưa. Nó gửi lại cùng key và payload; API đọc o7, trả 200 với ID ấy. Nếu browser tạo key mới, hệ thống không thể nhận ra đó là cùng một ý định và có thể tạo o8. Nếu nó dùng lại key nhưng đổi quantity, 409 là kết quả đúng: server từ chối gộp hai ý định khác nhau. Đây không phải trò chơi status code; nó là hợp đồng về danh tính của một hành động.

Có thể vẽ một lịch xen kẽ khác. Request A và B cùng key đến gần nhau; A nhận quyền viết trước, B chờ. A insert rồi commit. B đi vào transaction, thấy key đã tồn tại và trả ID của A nếu payload giống. Nếu A crash trước commit, transaction rollback; B sau đó có thể insert và trở thành người tạo record. Test cạnh tranh phải kiểm số record và ID trả về, vì chỉ thấy một response 201 và một response 200 trong một lần chạy chưa chứng minh mọi lịch đều đúng. Unique index giữ invariant cuối cùng ngay cả khi logic application có một race chưa nhìn thấy.

Idempotency cũng có phạm vi thời gian. Fixture giữ key suốt đời record, nên một request cũ gửi lại sau một tháng vẫn nhận cùng ID nếu dữ liệu còn. Một hệ production có thể xóa key sau thời hạn, nhưng khi ấy retry quá hạn có thể tạo hành động mới; client và API phải cùng biết chính sách. Nếu dữ liệu được phân vùng theo tenant, unique constraint nên gắn với tenant và loại hành động, không lấy một chuỗi toàn cầu làm danh tính. Nếu key có thể đoán và GET trả dữ liệu nhạy cảm, xác thực/ủy quyền vẫn phải bảo vệ response replay. Không nâng một demo đúng ở một database thành bảo đảm an toàn đa tenant.

Cuối cùng, một test chỉ kiểm HTTP mà không kiểm database có thể bỏ qua lỗi ghi hai row rồi trả một ID. Test này truy row count dưới cùng key, so payload hash và record origin. Nhưng ngay cả vậy, nó chưa thử mất điện đúng lúc fsync hoặc hỏng disk. SQLite transaction cho hợp đồng atomicity trong các điều kiện engine và filesystem hỗ trợ; độ bền thực tế còn phụ thuộc cấu hình journaling, storage và backup. Bài học cần giữ ranh giới: test logic đã chạy là bằng chứng về logic trên môi trường thử, không phải phép chứng minh tất cả điều kiện vật lý.
