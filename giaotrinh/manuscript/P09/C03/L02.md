State nối một địa chỉ Terraform với ID object ngoài đời. `import` dùng khi object đã tồn tại nhưng chưa được Terraform ở workspace này quản lý; nó không tạo object và không tự sinh cấu hình đúng ý định. `moved` diễn đạt đổi địa chỉ của object đã được quản lý khi refactor HCL. `terraform state mv` sửa ánh xạ state một lần bằng CLI; nó hữu ích cho thao tác đặc biệt nhưng dễ để code và state khác lịch sử nếu không có bản ghi thay đổi trong cấu hình. Ba công cụ giải ba tình huống khác nhau, không phải ba cách gọi của cùng một phép.

Giả định bucket `orders-archive-example` đã tồn tại ngoài Terraform. Trước import, xác nhận account, Region, tên/ID và ai đang quản lý bucket; sao lưu state hiện tại, giữ lock của backend và đối chiếu policy chặn destroy. Viết `resource` đúng địa chỉ dự định, thêm import block trỏ ID tương ứng, rồi đọc plan. Nếu plan vừa import vừa muốn sửa policy hoặc xóa versioning, đó là cảnh báo cấu hình chưa khớp trạng thái mong muốn; điều chỉnh HCL hoặc quyết định rõ thay đổi cần thiết trước apply. Sau import, đối chiếu state address với API object và chạy plan mới. Không import cùng object vào hai địa chỉ quản lý mà không chủ đích.

Nếu resource `aws_instance.orders` đang được quản lý nhưng đổi tên logic thành `aws_instance.api`, dùng `moved { from = aws_instance.orders to = aws_instance.api }` trong cấu hình. Plan phải thể hiện chuyển địa chỉ mà không định terminate instance chỉ vì đổi tên. Nếu plan vẫn đề xuất replace vì thuộc tính provider thay đổi, `moved` không chữa nguyên nhân ấy. Khi dùng `state mv` trong một sự cố, đóng băng các actor apply khác, sao lưu/version state, ghi lệnh và thời điểm, cập nhật HCL cùng review, rồi plan lại. Lock chỉ tuần tự hóa các actor dùng đúng backend; nó không khóa console hoặc workspace khác.

Địa chỉ là một phần của hợp đồng: module path, resource name và instance key đều phải chính xác. Thêm `count` hay `for_each` biến một địa chỉ đơn thành địa chỉ có index/key. Trước mỗi phép chuyển, viết bảng ánh xạ cũ → mới và ID ngoài đời, kiểm nó một-một; thiếu một dòng có thể khiến Terraform hiểu object cũ bị bỏ và object mới cần tạo. Một plan “0 to destroy” là điều kiện cần cho refactor giữ object, nhưng chưa chứng minh ứng dụng còn phục vụ đúng.
