Ở {{xref:P10.C02}}, một lần chạy Ansible quan sát rồi sửa cấu hình trên các máy đã chọn. Kubernetes đặt khai báo trong API để nhiều bộ điều khiển liên tục quan sát và sửa phần việc của mình. Người vận hành gửi `spec` mô tả điều muốn có; `status` là quan sát mà hệ thống cập nhật sau đó. Khoảng cách giữa hai phần là chuyện bình thường trong một thời gian, không phải bằng chứng `kubectl apply` đã thất bại. Ngược lại, API chấp nhận object cũng không chứng minh ứng dụng đã phục vụ. Muốn chẩn đoán phải lần theo đối tượng nào đã xuất hiện, ai chịu trách nhiệm bước kế tiếp, và điều kiện nào còn chưa đạt.

Giả sử ta khai báo Deployment `atlas` có hai bản sao. `kubectl` gửi yêu cầu đến API server. API server xác thực người gọi, kiểm tra quyền và qua các bước admission/validation áp dụng, rồi lưu object bằng kho trạng thái của cluster, thường là etcd. etcd giữ dữ liệu API; nó không chạy container và không phải kho dữ liệu của ứng dụng. Phản hồi apply thành công xác nhận yêu cầu khai báo đã được API chấp nhận, không phải xác nhận hai Pod đã chạy. Bản sao etcd và backup của nó liên quan đến khả năng khôi phục control plane; chúng không tự backup database bên trong workload.

Controller manager chạy các vòng điều khiển. Deployment controller thấy Deployment mới thì tạo hoặc điều chỉnh ReplicaSet; ReplicaSet controller tạo Pod để số bản sao tiến gần `spec.replicas`. Controller thường đọc/ghi qua API server thay vì trực tiếp mở tiến trình ứng dụng. Chọn node không có nghĩa image đã tải hoặc ứng dụng đã mở cổng. Runtime thực thi container, còn kubelet điều phối vòng đời Pod trên node. Network plugin và triển khai Service trên node tham gia đường truyền gói tin; không thể lấy kết quả scheduler làm bằng chứng đường dữ liệu đã thông.
